# 設計（これ 1 枚）

v0.3.0（2026-11-17）。文書は README（使う人）・CLAUDE.md（道しるべ）・本書（理由）の 3 つ。足す前に削る。

## 1. 何を解くか

非エンジニアのメンバーが、Team Standard 席（Sonnet 中心）で、データ整備・集計・計算・自動化 PoC を
**上長が後から検められ、FB を返せる形**で回す。指示書と履歴と学びは vault に溜まり、会話を消しても・人が替わっても辿れる。

| kind | 例 | メンバーの到達点 |
|---|---|---|
| `calc` | DB やリポジトリ内データを引いて集計・計算・判定し、決まった形の表にする（fs_mono_repo の outputs 系） | 完成まで |
| `auto` | 手作業の自動化（数式入り Excel・小さなプログラム） | MVP／PoC まで（本番化は上長側のハーネスへ） |

対象外: 設計文書を何本も持つソフトウェア開発（project_template の仕事）。

## 2. 構成 — 上長の vault / project_template をチーム用に写したもの

| 上長の構成 | チーム版 | 中身 |
|---|---|---|
| `vault`（第二の脳・指示書の正本） | **team vault**（別リポジトリ。上長の PC では個人 vault の下の 1 区画） | `projects/<プロジェクト名>/` = 指示書の正本、`AI/` = 共有の知識 |
| `project_template`（雛形の正） | **team-harness-kit**（このテンプレート） | ハーネス本体と指示書の雛形。版は `VERSION` |
| 各コードリポジトリ（コードのみ＋道しるべ） | **プロジェクトのリポジトリ**（1 つの ODSC に 1 つ） | ハーネス・プログラム・取得データ・成果物。`CLAUDE.md` は道しるべ |

team vault の区画と権限:

| 区画 | 書く人 | 中身 |
|---|---|---|
| `projects/<プロジェクト名>/` | そのプロジェクトの担当者とその AI（`FEEDBACK.md` だけは上長） | `ODSC.md`、`tasks/<ID>/`（spec・checks・plan・ロック・経過・Eval 結果・独立レビュー）、`records/`、`LEARNINGS.md`、`NEXT_SESSION.md`、`STATUS.md`、`FEEDBACK.md`・`FEEDBACK_RESPONSES.md`、実績 |
| `AI/` | 上長側だけ（蒸留）。メンバーの AI は読むだけ | `Decisions/RULES.md`（裁定）、`Knowledge/`（索引 = `00_Knowledge_MOC.md`）、`Lessons/` |

- 上長の個人 vault は非公開のまま。部下に見せない監査・評価のメモは個人 vault 側に置く。
- **PC ごとの場所は文書に書かない。** 道しるべは探す順（隣の `team-vault` → `.env` の `TEAM_VAULT` → 無ければ止まって尋ねる）だけを書く。
- プロジェクト名 = リポジトリのフォルダ名 = vault の `projects/` の下のフォルダ名。同じ名前の別プロジェクトは作れない。
- 取得データと成果物は GitHub に上げない（SQL・行数・ハッシュのみ）。DB は読み取り専用ロールで守る。

## 3. 流れ

```
プロジェクトで 1 回:  init（vault に指示書フォルダを雛形から作る）→ 聞き取り（ODSC → Customer）→ Review → odsc lock
タスクごと:          設計（仕様・検査・手順）→ 人が決定 → lock → 手順ごとに実装と確認 → Eval → 独立レビュー → close
会話の終わり:        save（NEXT_SESSION を上書きし、vault とリポジトリを GitHub へ）   会話の始まり: status（vault を pull）→ resume
上長:                team vault を pull → 現在地と記録を読む → FEEDBACK.md に書く → 必要なものだけ audit → LEARNINGS を AI/ へ蒸留
```

## 4. 仕組み

| 仕組み | 実体 | 狙い |
|---|---|---|
| 指示書は vault、コードは外 | ハーネスが読み書きの場所を分ける。指示書がコード側に書かれたら selftest が落ちる | 上長の構成と同じ。指示書が相互に辿れ、コードの作業ツリーは小さい |
| ODSC を先に決める | `ODSC.md`（Objective・Deliverable・Success Criteria・Customer・Review）をプロジェクトで 1 回決めてロック | 「正しいものを作ったか」の基準を固定する |
| タスクは SC を指す | 対応する Success Criteria の番号が無いとタスクをロックできない | 目的の外の仕事をプロジェクトに入れない |
| SDD | `spec.md`・`checks.json`・`plan.json` を先に書き、人が決定して `lock`。変更は理由付きの再ロックのみ | 判断を実装の前に寄せる。検査を弱めて通す抜け道を塞ぐ |
| Eval | `hk.py eval`（プログラム）。ロック後に ODSC・仕様・検査・手順が変わっていたら無条件 FAIL | 合否にモデルを使わない |
| 担当の分離 | 4.1 | メインの文脈を小さく保つ（効率）。経緯を知らない目で検算する（品質） |
| 範囲を守る | `step start`・`resume` が毎回 ODSC を表示。増えた論点は「SC に必要 → やる／気になる → `park`／目的が違った → ODSC を再ロック」。ロック後の作業時間が見積の 1.5 倍で警告 | 分析の広がりを止めずに、入れるかどうかを毎回決めさせる |
| 履歴と現在地 | 経過・Eval・ロックは vault に直接書かれる。`STATUS.md` はコマンドのたびに書き直し、`save` が `NEXT_SESSION.md` を上書きして push | `/clear` しても・別の PC でも・上長からも辿れる |
| 上長の FB | `FEEDBACK.md`（上長だけが書く）。書き込みがあると会話の最初に AI が知らせ、対応を `FEEDBACK_RESPONSES.md` に記録するまで知らせ続ける | 上長が vault に入って返した FB が、次の作業に必ず届く |
| 監査 | 上長側で `hk.py audit`（取り直し → `src/run.py` で作り直し → 検査し直し。タスクの履歴は書き換えない） | 途中に入らず、必要なものだけ再現する |
| 知識ループ | プロジェクトの `LEARNINGS.md`（追記のみ）→ 上長側が `AI/` へ蒸留し索引に 1 行 → 設計担当が次のタスクで読む → 雛形に反映して版を上げる | 回すほど共有の知識が濃くなる。蒸留の書き手は 1 人 |

### 4.1 担当とモデル

担当は「失敗の仕方が違うか」で分ける。人格・口調の文は持たない。

| 担当 | モデル | 起きやすい失敗 → 歯止め |
|---|---|---|
| メイン（聞き取り・進行） | Sonnet | 思いつきの順で聞く → 聞く順を固定 |
| designer（タスクの設計。1 タスク 1 回） | Opus | — Standard 席の枠を守るため 1 回だけ。呼べなければ Sonnet で書き、どちらで設計したかを記録 |
| Explore（探索） | Haiku | — |
| analyst（calc） | Sonnet | 行が黙って増減する・合わない行を消す・切り口を足す → 前後で件数と合計を出す、要確認で残す、park |
| automator（auto） | Sonnet | 値を貼っただけの数式・直書き・例外で黙って誤る → 人が出した正解との一致を基準にする |
| reviewer（独立点検） | Sonnet | 実装の説明に引きずられる → ODSC・仕様・成果物だけを渡し、別の方法で検算 |

### 4.2 分解・所要時間・履歴

| 何を | どう残すか | どこに集まるか（vault の `projects/<プロジェクト名>/`） |
|---|---|---|
| 分解 | `plan.json`（手順 = fetch / shape / calc / build / verify の 1 種類、見積 30 分以内、最大 8 手順） | `tasks/<ID>/plan.json`、`_STEPS.csv` |
| 所要時間 | `hk.py` の全コマンドが `events.jsonl` に時刻を残す。間隔を 30 分で頭打ちにして足したものが作業時間 | `tasks/<ID>/events.jsonl`、`_LEDGER.csv`、`_STEPS.csv` |
| 履歴 | `hk.py note`（try / fix / decide / block / design / park）、Eval の毎回の結果、再ロックの理由 | `tasks/<ID>/log.md`・`eval.json`・`lock.json`、閉じたら `records/<ID>.md` |
| 集計 | `hk.py stats`（全プロジェクト横断。担当 × 種類 × 設計モデル別、手順の種類別） | 標準出力か `--out` |

作業時間は近似（`hk.py` を 30 分以上呼ばずに作業した時間は落ちる。人と AI の時間は分けていない）。
イベントの形（`at` / `event` / 付帯項目、1 行 1 件）はツールに依らないので、project_template に同じ形で持ち込める。

## 5. 上長の構成と変えたところ

| 上長の構成 | チーム版 | 理由 |
|---|---|---|
| 指示書 12 文書（MASTER・PROJECT・ARCHITECTURE・PATTERNS・PROCESS・DECISIONS …） | `ODSC.md` とタスクごとの spec・checks・plan | 小さな集計・PoC が対象。構造の設計が要る大きさは対象外 |
| 道しるべは極小、規則は vault の指示書 | 道しるべに「守ること」を持つ | 規則は全プロジェクトで同じ。プロジェクトごとの写しを持たない |
| `new-project.ps1` が雛形側から vault とコードの両方を作る | リポジトリはテンプレートから作り、`init` が vault 側を作る | メンバーは「始める」と言うだけで済む |
| 絶対パスを道しるべに書く | `.env` に逃がす | PC ごとに場所が違う |
| Superpowers の工程 | `task` スキル 1 本 | 非エンジニアの小タスクには過大。`auto` の PoC が 3 本続けて「仕様は正しいのに実装が通らない」で止まったら、実装の進め方だけ足す |
| Risk Assessment、Strategy & Tactics の Assumption | 持たない | 設計を重くしない。監査で「目的に合わない」「前提が違っていた」が 10 タスク中 3 件以上で戻す |
| `HUMAN/` 区画 | 持たない | 必要になったら足す |

## 6. 効いているかの測り方（外れたら設計を変える）

`hk.py stats` と監査結果から月次で見る。

| 仮説 | 測るもの | 棄却の目安 |
|---|---|---|
| Sonnet で calc タスクは回る | 初回 Eval 通過率、Eval 回数 | 10 タスクで初回通過 3 割未満かつ平均 4 回超 |
| 設計を Opus にすると手戻りが減る | 設計モデル別の修正回数・再ロック回数・Eval 回数 | 各 10 タスクで差が無い → Opus をやめる |
| ODSC・Customer・Review で足りる | 計画・設計の時間、監査で「目的に合わない」「前提が違っていた」の件数 | 10 タスク中 3 件以上 → Risk か Assumption を戻す |
| 1 プロジェクト 1 ODSC の粒度は合っている | プロジェクトあたりのタスク数、ODSC の再ロック回数、park の件数 | タスク 1〜2 本で終わるプロジェクトが大半 → 細かすぎる。ODSC の再ロックが頻発 → 粗すぎる |
| 範囲のずれを抑えられている | 実績÷見積、見送り件数、再ロック回数 | 実績÷見積が 1.5 超なのに見送り・再ロックがほぼゼロ → 黙って広げている |
| FB は届いて効く | FB から対応の記録までの日数、同じ指摘の再発 | 対応の記録が形だけ（同じ指摘が 3 回）→ FB を裁定か検査に上げる |
| 履歴で再開できる | `/clear` 後に人が説明し直した回数、`save` 無しで終わった会話 | 説明し直しが常態 → resume の中身か save の強制を直す |
| Eval PASS は信用できる | 監査で見つかった誤り ÷ PASS したタスク | 2 割超 → 検査の書き方か reviewer を直す |
| 学びは使われる | `AI/` に上がった件数、次のタスクの仕様・検査に引かれた回数 | 1 か月ゼロ → 学びの取り方か蒸留の頻度を変える |

## 7. 既知の限界

- Claude Code 上での実走は未確認（`hk.py` は selftest 済み。スキル・サブエージェント・フック・permissions・`additionalDirectories` の相対パスは未走行）。
- AI がリポジトリの外（team vault）に書く。他のプロジェクトや `AI/`・`FEEDBACK.md` に書かないことは、道しるべの規則で守らせている（Claude Code の権限では止めていない）。
- 範囲の分類、手順・修正の記録、`save` は AI がコマンドを呼ぶ前提。呼び忘れると履歴と統計が欠ける。
- 仕様の変更（vault）とコードの変更（リポジトリ）は別々のコミットになる。対応はロックの履歴とタスク番号で辿る。
- team vault は全員が同じリポジトリに push する。プロジェクト別のフォルダで衝突を避けている。
- 1 プロジェクトの担当者は 1 人の前提。
- Excel の書式は meltec-excel を正とし、Eval は数字だけを `summary.csv` 経由で検査する。
